1. Visión general y alcance

Sistema web de reservas de hotel. Un visitante explora hoteles y habitaciones; un usuario registrado reserva con una tarjeta (nueva o guardada), consulta y cancela sus reservas; un administrador gestiona el inventario y consulta la previsión de demanda. El proyecto parte del repositorio de código abierto de natanael-lima y se amplía con tres historias obligatorias del curso y dos extra elegidas por el equipo.

2. Arquitectura

Frontend (SPA)

React 18 + Vite 5 + TypeScript + Tailwind + React Router 6. Un único cliente HTTP (axios, services/axiosConfig.ts) con interceptor 401/403. Vitest + Testing Library.

Backend (API REST)

Spring Boot 3.3.2, Java 17. Capas: controller → service/service/imp → repository → entity. Lógica pura en domain/. JWT stateless.

Datos

H2 en modo PostgreSQL para dev/test (con datos de ejemplo). PostgreSQL real con perfil postgres y docker-compose.yml.

Decisiones de arquitectura (ADR): JWT stateless (001); H2 en dev/test y PostgreSQL real (002); pasarela de pago simulada con tokenización (003); algoritmo de previsión de demanda (004); disponibilidad derivada de las reservas (005); reloj inyectable y zona horaria de check-in (006); base developer en lugar de main (007).

Reglas transversales: errores con un único sobre ApiResponse{message, code, errors}; dinero en enteros (USD); Clock inyectable (zona America/Panama, check-in 15:00, máximo 30 noches); un recurso ajeno responde 404, no 403.

4. Seguridad y roles

  • Autenticación: POST /auth/login devuelve un JWT (claim uid). El secreto se lee de app.jwt.secret (Base64); fuera de dev/test no tiene valor por defecto.
  • Autorización: SecurityConfig declara cada ruta pública de forma explícita; el resto exige autoridad USER o ADMIN (hasAuthority, sin prefijo ROLE_).
  • Propiedad: tarjetas y reservas se filtran por el usuario del token; un recurso ajeno responde 404.
  • Datos sensibles: el número completo y el CVV nunca se persisten ni aparecen en logs (probado con SensitiveDataTest).
  • Anónimo en ruta protegida: 401; autenticado sin permiso: 403.

5. Flujos del sistema

5.1 Acceso (login y roles)

1. LoginEl usuario envía email y contraseña a /auth/login.
2. TokenEl backend valida con BCrypt y devuelve el JWT con uid.
3. SesiónAuthContext guarda token, usuario y rol (/api/user/current).
4. RutasProtectedRoute exige rol; el panel admin solo entra ADMIN.
Token inválidoEl interceptor recibe 401/403 y cierra la sesión.

5.2 Consulta de disponibilidad (calendario)

1. DetalleEl visitante abre una habitación.
2. ConsultaEl hook useAvailability pide get-availability/{id}?from&to de los dos meses visibles.
3. CálculoOccupancyCalculator marca como ocupadas las noches de reservas CONFIRMED.
4. SelecciónEl calendario pinta libres/ocupados y valida el rango (máx. 30 noches, sin cruzar ocupadas).
5. Book nowCon rango válido se habilita la reserva.

5.3 Reservar con tarjeta guardada o nueva

1. PagoEl modal muestra la tarjeta predeterminada (un clic) o un formulario de tarjeta nueva con «guardar».
2. ValidaciónPOST /api/reservation/book: formato (400), fuente de pago única, Luhn/marca/CVV/vencimiento (422), fechas y huéspedes (422).
3. BloqueoSe bloquea la fila de la habitación y se comprueba el solape.
ConflictoFechas ya reservadas → 409, no se cobra.
4. CobroPasarela simulada (tok_, txn_). La tarjeta terminada en 0002 se rechaza → 402 y no se guarda nada.
5. ConfirmaciónSe crean Reservation + Payment en una transacción; si pidió guardar, se guarda el token. Respuesta 201 con Location.

5.4 Mis reservas y cancelación (HU-05, pendiente)

1. ListadoGET /api/reservation/my-reservations devuelve solo las del usuario.
2. CancelarPUT /api/reservation/cancel-reservation/{id}.
3. PolíticaCancellationPolicy: con 48 h o más antes del check-in, reembolso total; si no, sin reembolso.
4. ResultadoReserva CANCELLED, noches liberadas y Payment REFUNDED cuando corresponde.

5.5 Previsión de demanda (HU-03, parcial)

1. HistóricoOcupación mensual de 24 meses derivada de las reservas.
2. ModeloDemandForecastCalculator: regresión lineal (OLS) con estacionalidad mensual (ADR-004).
3. ReglasPricingRules: ajuste de precio sugerido y acción de inventario.
4. GráficosEl panel admin muestra previsión, estacionalidad y tabla (recharts) — por completar.

7. Cambios implementados por historia de usuario

HU-00 — Base técnica Mergeada · PR #8

  • Se eliminó bin/ versionado y se corrigieron 37 errores de TypeScript para que tsc -b compile.
  • Perfiles dev (H2), test y postgres, más docker-compose.yml.
  • User.role pasó de ordinal a texto.
  • Errores unificados con ApiResponse, BusinessException, ConflictException, ResourceNotFoundException y GlobalExceptionHandler.
  • CI en GitHub Actions (backend y frontend), Vitest configurado y ExistingApiCharacterizationTest que fija el comportamiento previo.

HU-01 — Reservar con datos de pago guardados Mergeada · PR #13

  • Dominio: CardValidator (Luhn, marca VISA/MASTERCARD/AMEX, CVV, vencimiento, checkFormat) y CancellationPolicy, ambos sin dependencias de Spring.
  • Modelo y servicios: PaymentMethod, PaymentMethodService, PaymentGateway simulada y BookingService.book.
  • API: /api/payment-method/* y POST /api/reservation/book (201 + Location).
  • Concurrencia: bloqueo pesimista de la habitación (también en las reservas del admin) y aislamiento READ_COMMITTED.
  • Frontend: ConfirmBookingModal como paso de pago, CardForm, PaymentMethodSelector y PaymentMethodsPage (/payment-methods).
  • Revisión: el agente senior-architect-backend aprobó con cambios; se corrigió la fuga de PAN/CVV en el log DEBUG de Bean Validation.
  • Pruebas: BookingTest (15), SensitiveDataTest (2), CardValidatorTest, CancellationPolicyTest; frontend 71 tests.

HU-02 — Calendario dinámico Mergeada · PR #11 y #12

  • Disponibilidad derivada de las reservas CONFIRMED con OccupancyCalculator (noche ocupada si start ≤ d < end).
  • Reservation con LocalDate y ReservationStatus; solapes → 409/422 también en las reservas del admin.
  • GET /api/room/get-availability/{id} y get-all?activeOnly; datos de ejemplo de 2 hoteles, 8 habitaciones y 60 días de reservas.
  • Frontend: components/calendar/* (calendario propio de dos meses), RoomDetailsPage con precio por noches.
  • Fix #12: un test intermitente del CI (RoomDetailsPage) se corrigió desmontando antes de resetear los mocks.
  • Pruebas: RoomAvailabilityTest y 49 tests de frontend.

HU-03 — Previsión de demanda Parcial · sin PR

  • Hecho: DemandForecastCalculator (OLS con tendencia y estacionalidad mensual sobre 24 meses), PricingRules y OccupancyCalculator.nightsPerMonth, con pruebas en verde que usan los vectores del ADR-004.
  • Falta: DTO, servicio y controlador (GET /api/analytics/demand-forecast?horizon&hotelId), datos históricos de 24 meses y los gráficos con recharts.

HU-04 — Control de acceso por roles Mergeada · PR #9 y #10

  • SecurityConfig con la matriz de permisos; se eliminó el GET público global que exponía usuarios y pagos.
  • JWT con secreto configurable y claim uid; el filtro tolera tokens inválidos o caducados.
  • CurrentUserService, AdminBootstrap y datos de ejemplo (admin@hotel.com y demo@hotel.com).
  • Revisión: el agente rechazó la primera versión por 3 críticos (mass assignment de id, pagos accesibles a USER, toma de cuenta por renombrado); se corrigieron con tests.
  • Frontend: AuthContext, ProtectedRoute por rol, AdminLoginPage, interceptor 401/403.
  • Fix #10 (SonarCloud S7044/S8476): toPathId valida los ids antes de armar URLs.

HU-05 — Mis reservas y cancelación Pendiente

  • Reutilizará BookingService.toMyReservation y CancellationPolicy.
  • Falta: GET /api/reservation/my-reservations, PUT /api/reservation/cancel-reservation/{id} (reembolso con 48 h o más), la página Bookings real y sus tests.

9. Cómo ejecutarlo

  • Backend (dev, H2): cd hotel-reservation-system-backend && ./mvnw spring-boot:run (puerto 3000). Usuarios de ejemplo: admin@hotel.com / Admin12345, demo@hotel.com / Demo12345.
  • Backend (PostgreSQL): docker compose up -d y perfil postgres con app.jwt.secret definido.
  • Frontend: cd hotel-reservation-system-frontend && npm ci && npm run dev.
  • Pruebas: ./mvnw test y npx vitest run.
