## Historia

**Como** administrador del sistema, **quiero** que solo las cuentas ADMIN puedan gestionar hoteles, habitaciones, usuarios, pagos y ver la analítica, **para** proteger el inventario y los datos de los huéspedes.

## Descripción y valor

En `developer`, cualquier GET es público (incluidos el listado de usuarios, pagos y reservas) y cualquier usuario autenticado puede crear, editar o borrar hoteles, habitaciones y usuarios. El secreto JWT está en el código, el anónimo recibe 403 en lugar de 401, un token caducado rompe la petición y el panel `/admin/dashboard` solo comprueba que haya token. Esta HU aplica la matriz RBAC del contrato en el backend y en la SPA, y cierra los hallazgos de la revisión de seguridad (ARCHITECTURE §2.1 B1–B9, §2.2 F3–F5). El valor es que un huésped no puede alterar el inventario ni leer datos personales o de pago de otros.

## Reglas de negocio

- RN-04.1: El acceso sigue la matriz de [API-CONTRACT §13](../architecture/API-CONTRACT.md#13-matriz-rbac). Las rutas públicas se listan una a una; todo lo demás exige autenticación, y las rutas de gestión exigen la autoridad `ADMIN` (`hasAuthority`, sin prefijo `ROLE_`).
- RN-04.2: Anónimo en ruta protegida → `401 UNAUTHORIZED`. Autenticado sin permiso → `403 FORBIDDEN`. Recurso de otro usuario en rutas "dueño" → `404`. Siempre con el sobre `ApiResponse`.
- RN-04.3: El rol se lee de la BD en cada petición. Ningún claim del token concede privilegios. `role` se guarda como texto (`STRING`).
- RN-04.4: Ningún endpoint permite autoasignarse ni asignar `ADMIN`: el registro público y `/api/user/registration-user` crean `USER`, y `update-user` ignora `role`. Los ADMIN solo se crean con el seed `dev` o con `AdminBootstrap` en `postgres` (ARCHITECTURE §4.3).
- RN-04.5: El secreto JWT viene de `JWT_SECRET`. En el perfil `postgres` no hay valor por defecto: sin él, la aplicación no arranca.
- RN-04.6: Un token caducado, mal firmado, alterado o de un usuario borrado se trata como ausente (401 en protegidas; se ignora en públicas).
- RN-04.7: El login fallido responde igual exista o no el usuario, y en ambos casos se ejecuta el hash de contraseña.
- RN-04.8: Los errores de negocio 4xx (no encontrado, validación, conflicto) nunca se devuelven como 500.
- RN-04.9: En la SPA, `/admin/dashboard` exige `ADMIN`; `/bookings` y `/payment-methods` exigen sesión. `AdminLoginPage` rechaza cuentas no ADMIN.

## Criterios de aceptación

```gherkin
Escenario: CA-04.1 Anónimo en una ruta protegida
  Cuando hago GET /api/user/get-all sin cabecera Authorization
  Entonces la respuesta es 401 con {"message": "...", "code": "UNAUTHORIZED"}

Escenario: CA-04.2 Huésped en rutas de gestión
  Dado un token válido de "demo@hotel.com" (USER)
  Cuando llamo a POST /api/hotel/registration-hotel, PUT /api/room/update-room/1, GET /api/user/get-all, GET /api/payment/get-all o GET /api/analytics/demand-forecast
  Entonces cada respuesta es 403 con code "FORBIDDEN"
  Y la base de datos no cambia

Escenario: CA-04.3 El administrador gestiona
  Dado un token válido de "admin@hotel.com" (ADMIN)
  Cuando creo un hotel, edito una habitación y listo usuarios y pagos
  Entonces las respuestas son 200

Escenario: CA-04.4 Lo público sigue público
  Cuando hago GET /api/hotel/get-all, GET /api/room/get-room/1 o GET /api/review/get-all sin token, o con un token caducado
  Entonces ninguna respuesta es 401 ni 403
  Y POST /auth/login y POST /auth/registration-user siguen funcionando sin token

Esquema del escenario: CA-04.5 Matriz RBAC completa
  Dado el actor <actor>
  Cuando llama a <método> <ruta>
  Entonces el estado es <esperado>
  Ejemplos:
    | actor   | método | ruta                                    | esperado |
    | anónimo | GET    | /api/payment/get-all                    | 401      |
    | USER    | DELETE | /api/user/delete-user/2                 | 403      |
    | USER    | GET    | /api/reservation/get-all                | 403      |
    | ADMIN   | GET    | /api/reservation/get-all                | 200      |
    | anónimo | GET    | /api/room/get-availability/1?from=...   | 200      |
  # El test parametrizado recorre TODAS las filas de API-CONTRACT §13 para los tres actores.

Escenario: CA-04.6 Recursos del propio usuario
  Dado dos usuarios USER, A (id 7) y B (id 8)
  Cuando A hace GET /api/user/get-user/7, recibe 200
  Y cuando A hace GET /api/user/get-user/8 o PUT /api/user/update-user/8, recibe 404 con code "USER_NOT_FOUND"
  Y cuando A hace PUT /api/user/update-user/7 cambiando username, su username no cambia
  Y cuando un ADMIN cambia el username de B a un email ya registrado, recibe 409 con code "USERNAME_ALREADY_EXISTS"

Escenario: CA-04.7 Nadie se autoasigna ADMIN
  Cuando me registro en /auth/registration-user enviando "role": "ADMIN"
  Entonces GET /api/user/current devuelve role "USER"
  Y si un USER hace PUT /api/user/update-user/<su id> con "role": "ADMIN", su rol sigue siendo "USER"
  Y si un ADMIN crea un usuario con /api/user/registration-user enviando "role": "ADMIN", el usuario creado es "USER"

Escenario: CA-04.8 Tokens inválidos
  Cuando llamo a GET /api/user/current con un token caducado (Clock fijo), firmado con otra clave, con el payload alterado, o de un usuario ya borrado
  Entonces la respuesta es 401 con code "UNAUTHORIZED" (nunca 500)

Escenario: CA-04.9 El rol no sale del token
  Dado un token firmado con la clave correcta para un USER al que se añadió el claim "role": "ADMIN"
  Cuando llama a GET /api/user/get-all
  Entonces la respuesta es 403

Escenario: CA-04.10 Secreto externalizado
  Dado el perfil "postgres" sin la variable JWT_SECRET
  Cuando arranca la aplicación
  Entonces el arranque falla con un mensaje que nombra JWT_SECRET
  Y un token firmado con la antigua constante de JwtServiceImp es rechazado con 401

Escenario: CA-04.11 Login sin enumeración

  Y en ambos casos se invoca PasswordEncoder.matches exactamente una vez

Escenario: CA-04.12 Los 4xx no se convierten en 500
  Dado un token ADMIN
  Cuando hago PUT /api/hotel/update-hotel/999 o DELETE /api/room/delete-room/999
  Entonces la respuesta es 404 con code "HOTEL_NOT_FOUND" o "ROOM_NOT_FOUND"
  Y cuando registro un email ya existente en /auth/registration-user, la respuesta es 409 con code "USERNAME_ALREADY_EXISTS"

Escenario: CA-04.13 Alta del primer ADMIN en PostgreSQL
  Dado el perfil "postgres", una base sin ADMIN y las variables ADMIN_USERNAME y ADMIN_PASSWORD
  Cuando arranca la aplicación

Escenario: CA-04.14 Login de administración rechaza a huéspedes

  Cuando inicio sesión con "demo@hotel.com" (USER)
  Entonces veo "Esta cuenta no tiene permisos de administrador", no navego a /admin/dashboard y el token se borra

Escenario: CA-04.15 Rutas protegidas en la SPA
  Dado que inicié sesión como USER
  Cuando navego a /admin/dashboard, soy redirigido a "/"

Escenario: CA-04.16 Sesión caducada durante el uso
  Dado que tengo sesión y el backend responde 401 UNAUTHORIZED
  Entonces el interceptor de axios borra localStorage["token"] y la SPA vuelve a pedir inicio de sesión

Escenario: CA-04.17 El CRUD de hoteles del panel funciona con token
  Dado que inicié sesión como ADMIN en el panel
  Cuando creo y edito un hotel desde HotelFormAdd/HotelFormEdit
  Entonces la petición lleva "Authorization: Bearer <token>" y la operación se completa
```

## Endpoints y pantallas

- Endpoints: todos los de la matriz [API-CONTRACT §13](../architecture/API-CONTRACT.md#13-matriz-rbac); cambios de error en `/auth/login`, `/auth/registration-user` y `/api/user/current` ([§2](../architecture/API-CONTRACT.md#2-autenticación)); `userId` del token en `/api/review/registration-review` (§8).
- Pantallas: `AdminLoginPage`, `DashboardPage` (vía `ProtectedRoute role="ADMIN"`), `Header` (modal de login con `?login=1&redirect=`), `ProfileCircle`/`ProfileCircleAdmin` (logout), formularios de hotel del panel.

## Tareas técnicas

**Backend**
- [ ] `SecurityConfig`: quitar `requestMatchers(HttpMethod.GET).permitAll()`; listar rutas públicas; `hasAuthority("ADMIN")` según la matriz; permitir `/error` y `OPTIONS`; `AuthenticationEntryPoint` (401) y `AccessDeniedHandler` (403) con `ApiResponse`; CORS central (si HU-00 no lo dejó hecho).
- [ ] `jwt/JwtServiceImp`: secreto desde `app.jwt.secret` (`JWT_SECRET`), expiración configurable, `Clock` inyectado (`Jwts.parserBuilder().setClock(...)`). Perfiles: `dev`/`test` con valor fijo de ejemplo; `postgres` con `${JWT_SECRET}` sin valor por defecto.
- [ ] `jwt/JwtAuthenticationFilter`: `try/catch` de `JwtException` y `UsernameNotFoundException` → no autenticar y continuar.
- [ ] `entity/User`: `@Enumerated(EnumType.STRING)` en `role`; `@ToString.Exclude`/`@EqualsAndHashCode.Exclude` en las relaciones; eliminar `orElseThrow()`.
- [ ] `AuthController`/`AuthServiceImp`: `@Valid` en `RegisterRequest` (email, contraseña 8–72 con letra y dígito, `fullName` opcional ≤ 100); `ConflictException("USERNAME_ALREADY_EXISTS")`; username en minúsculas; `BadCredentialsException` → 401 `INVALID_CREDENTIALS` en `GlobalExceptionHandler`. La forma `{token}` en caso de éxito no cambia.
- [ ] `UserController.getCurrentUser` y servicios "dueño": `get-user/{id}` y `update-user/{id}` comparan con el usuario del token (ADMIN pasa); ajeno → `ResourceNotFoundException("USER_NOT_FOUND")`. En `updateUser`, ignorar `username` si quien llama no es ADMIN y validar duplicado → `ConflictException("USERNAME_ALREADY_EXISTS")`.
- [ ] `ReviewServiceImp.createReview`: `userId` desde el token.
- [ ] Quitar los `try/catch(Exception)` de `HotelController`, `RoomController`, `UserController`, `ReservationController`, `PaymentController` y `ReviewController`; los servicios lanzan `ResourceNotFoundException` con su `code`.
- [ ] `configuration/AdminBootstrap` (`@Profile("postgres")`, `ApplicationRunner`, `ADMIN_USERNAME`/`ADMIN_PASSWORD`, idempotente).
- [ ] Actualizar en el mismo PR las expectativas de los tests de caracterización de HU-00 que cambian (403→401, 500/204→404, 400→409), para que el cambio sea visible en la revisión.

**Frontend**
- [ ] `services/hotelService.ts` → instancia axios `api` (lleva el token). Recomendado: también `authService.ts`, conservando `localStorage['token']`.
- [ ] `services/axiosConfig.ts`: interceptor de respuesta para 401 (borra el token y emite `auth:logout`). `services/apiError.ts` (`toApiError`).
- [ ] `contexts/AuthContext.tsx`: `user` (de `getCurrentUser()`), `isAdmin`, `login` que carga el usuario y escucha `auth:logout`.
- [ ] `routes/ProtectedRoute.tsx`: prop `role?: 'ADMIN' | 'USER'`; sin sesión → `/admin/login` (admin) o `/?login=1&redirect=` (huésped); rol insuficiente → `/`.
- [ ] `pages/RegisterPage.tsx`: mostrar los `errors` por campo del 400 y la regla de contraseña bajo el campo (el input ya es `type="email"`).
- [ ] `pages/AdminLoginPage.tsx`: tras el login, si `!isAdmin` → mensaje, `logout()` y quedarse en la página.
- [ ] `components/Layouts/Header.tsx`: abrir el modal de login si `?login=1` y navegar a `redirect` tras el éxito. `App.tsx`: `/admin/dashboard` con `role="ADMIN"`; `/bookings` y `/payment-methods` con `role="USER"`.
